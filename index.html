The paper in the box that says what shipped.

A vendor publishes one signed document per release. Any consumer verifies it with one pinned key and gets checksums, platforms, provenance links, and an evidence level.

01 · The problem

Every installer re-invents release verification, badly.

Checksums over TLS prove nothing

Most tools download a SHASUMS256.txt from the same place as the binary. If the release page is hijacked, the checksums are hijacked with it. The digest matches and the malware installs.

Per-vendor logic does not scale

Package managers, registries, and corporate mirrors each hand-code how vendor X signs, where vendor Y puts the checksum file, and which name means aarch64. It rots, and nobody audits it.

No shared notion of evidence

"Signed" means anything from a GPG signature on a checksum file to full SLSA provenance. Without a common scale, a consumer cannot enforce a floor or notice when a release quietly gets weaker.

02 · How it works

One document, one key, one verifier.

The vendor creates it in CI

After building release artifacts, one command digests them, infers platforms from file names, and signs the result with the vendor's release key.

packslip create \
  --project pkg:github/o/r \
  --version 1.2.3 \
  --key release.key \
  --out dist dist/*.tar.xz

It ships beside the artifacts

packslip.json and packslip.json.minisig are uploaded as release assets, or placed under the version directory of a download site. Optionally a signed list of recent releases lives at a well-known URL on the vendor's domain.

The consumer pins the key once

A registry entry, a repository's upstream declaration, or a tool option records the public key. Every release after that is verified against it. The key never comes from the document.

packslip verify packslip.json \
  --pubkey vendor.pub \
  --artifact r-1.2.3-linux-x64.tar.xz

The document is an in-toto Statement v1 with a packslip predicate, so it fits the attestation tooling that already exists. The signature is a plain minisign signature over the file bytes, so minisign -V -p vendor.pub -m packslip.json verifies it with no packslip tooling at all.

03 · Evidence levels

A shared scale for what a release proves.

Consumers use the level to enforce a floor and to refuse downgrades: a release that arrives with weaker evidence than the previous one is rejected until a human says otherwise.

LevelMeaningWho establishes it
L0Checksums only, no signature.Legacy releases.
L1Signed checksums or per-artifact signatures.Legacy releases.
L2A signed packslip.packslip verify
L3L2 plus per-artifact build provenance (SLSA, sigstore bundles) that the consumer verified.packslip verify reports L3 when every artifact links provenance; the consumer verifies the bundles.
L4L3 plus reproducible or independently verified builds.The consumer, from evidence it gathers elsewhere.
04 · Adoption

Publishing takes one CI step. Consuming takes five rules.

For vendors

Install the tool, generate a release key once, and keep the secret half in your CI secret store.

cargo install --git https://github.com/jdx/omapac packslip

packslip keygen -o release.key
# wrote release.key and release.pub (key id 5A0A0B8B9C6D7E1F)

Commit release.pub to your repository and mention it in your README, so consumers have somewhere to pin from. Then, in the release job, after the artifacts exist:

packslip create \
  --project pkg:github/jdx/mise \
  --version "$VERSION" \
  --key release.key \
  --out dist \
  --url-base "https://github.com/jdx/mise/releases/download/v$VERSION" \
  --source-repo https://github.com/jdx/mise \
  --tag "v$VERSION" \
  --commit "$GITHUB_SHA" \
  --supersedes "$PREVIOUS_VERSION" \
  dist/*.tar.xz dist/*.zip

Platforms are inferred from file names; write path:os/arch[/libc] to override one. Add --provenance URL once per artifact, in the same order, if you publish build provenance. Upload dist/packslip.json and dist/packslip.json.minisig with the release.

Optional: serve a signed list of recent releases at https://<your-domain>/.well-known/packslip/<project>.json so consumers can discover new versions without a registry.

For consumers

Whether you are a package manager, a distribution repository, or a corporate mirror, the same rules apply.

  1. Pin the identity once. Record the vendor's public key in your registry, upstream declaration, or tool config. Never take the key from the document.
  2. Verify in order. The signature, then the document structure, then the subject digest and size of every artifact you downloaded.
  3. Enforce no-downgrade. Refuse a release whose identity scheme is weaker than the last accepted one, or that dropped per-artifact provenance the last release carried.
  4. Apply a minimum release age to published_at, so a hijacked release has time to be noticed before unattended installs pick it up.
  5. Treat supersedes as the ordering hint for rollback detection. Never parse version strings.
packslip verify packslip.json --pubkey vendor.pub \
  --artifact mise-v2026.9.1-linux-x64.tar.xz --json
{
  "project": "pkg:github/jdx/mise",
  "version": "2026.9.1",
  "published_at": "2026-09-01T12:00:00Z",
  "key_id": "5A0A0B8B9C6D7E1F",
  "level": "l2",
  "checked_artifacts": ["mise-v2026.9.1-linux-x64.tar.xz"],
  "artifact_count": 6
}

The verifier is also a Rust library: packslip::verify(document, signature, &pubkey, &artifacts) returns the same structure, and packslip schema prints the JSON schema for other languages.

05 · Who uses it

Built for the tools that install other people's binaries.

omapac and the Omarchy Package Repository

Vendor-built packages are generated from the vendor's packslip instead of hand-edited checksum lines. The repository re-verifies against the pinned key, enforces a minimum release age and an evidence floor, and ships the packslip as a sidecar so clients can chain repository signature to vendor identity offline.

mise

mise's own release workflow is intended to be the first publisher and the reference implementation. Its github and http backends will verify a packslip when one is present and record the evidence level in mise.lock.

Everyone else

The name is neutral on purpose and the format carries no distro or vendor specifics. aqua, Homebrew, a corporate mirror, or a one-off install script can all verify the same document with the same pinned key.
