Work in progress. packslip is a draft, not a standard. mise ships experimental support for it, but the format and the tooling still change between releases, so use it for testing and nothing you depend on. Expect breaking changes until it is declared stable.

Version 1 · draft

A release manifest anyone can verify.

packslip is one signed file beside your artifacts. It says which file is for which platform, what goes on PATH, where the build provenance lives, and what else came along, from completions to a desktop entry. Your release job signs it with no key to manage, and any installer verifies it against your repository name with no registry entry.

01 · The problem

Every installer re-invents release verification, badly.

Checksums over TLS prove nothing

Most tools download a SHASUMS256.txt from the same place as the binary. If the release page is hijacked, the checksums are hijacked with it. The digest matches and the malware installs.

Registries take the vendor out of the loop

Package managers keep a central pile of YAML describing how each vendor names its assets, where its checksums live, and which file is the binary. The vendor has no say in it, and every entry rots. A manifest the vendor signs keeps the vendor in charge of its own tool: an installer reads the release directly, and a package manager like pacvamp can still repackage it with the vendor's provenance intact.

Build provenance says how, not what

SLSA provenance proves an artifact came out of a given build. It does not say which artifact is for which platform, what to put on PATH, or what else shipped in the release: the shell completions, the man page, the agent skill, the desktop entry or app bundle for a GUI. That gap is what a manifest fills.

02 · How it works

The vendor describes the release. The forge vouches for the vendor.

The release job signs it

Add one step after the artifacts are built. It attests their build provenance, hashes them, works out each platform from the file name, and signs the manifest through sigstore with the workflow's own identity. No secret is created or stored.

- uses: jdx/packslip@v1
  with:
    artifacts: dist/*
    bin: mise

One file ships beside the artifacts

packslip.sigstore.json becomes a release asset. It is an ordinary sigstore bundle: the statement, the certificate naming the workflow that signed it, and the Rekor log entry proving when. cosign and gh attestation read it as-is.

The consumer checks the name

A packslip for github.com/jdx/mise must be signed by a workflow of that repository through GitHub's issuer. The project name is the pin. There is nothing to configure on first use and nothing to look up in a registry.

packslip verify packslip.sigstore.json \
  --artifact mise-v2026.9.1-linux-x64.tar.xz

packslip invents as little as it can. The document is an in-toto statement inside a sigstore bundle, the same shape GitHub artifact attestations, npm provenance, and Homebrew bottles already use, so the tools that read those read this too. Identity comes from sigstore's certificate authority and transparency log. The only new part is the payload: the release manifest itself.

03 · Names

One name says where the release lives and who may sign it.

github.com/jdx/mise

Releases and their packslips are GitHub release assets. The signer must be a workflow of that repository, through GitHub's OIDC issuer. gitlab.com/group/tool works the same way, through GitLab's own issuer.

mise.jdx.dev

The vendor owns the domain and publishes a signed release list at /.well-known/packslip.json. The list names each release's packslip and its digest, and carries an expiry and a sequence number, so a mirror cannot freeze or roll back what consumers see.

github.com/oxc-project/oxc/oxlint

A repository that ships several tools adds the tool's name to the path. Each tool then gets its own packslip and its own version number, even when one release carries all of them, so an installer asking for oxlint 1.9.4 finds exactly that file. The signer is still checked against the repository.

04 · What it proves

The packslip proves the manifest. SLSA proves the build.

A verified packslip proves what shipped

The named signer published exactly this list of artifacts, with these digests, platforms, and bundled resources, at a time the transparency log recorded. A hijacked release page cannot change it, and a release that was rolled back or quietly removed shows up as such.

Linked provenance proves how it was built

Each artifact can link to its SLSA build provenance. A consumer that verifies those statements gets whatever build level the builder provides. On GitHub-hosted runners that is Build L2, or L3 when the build runs in a reusable workflow, and the packslip action produces the provenance for you.

Consumers set their own bar

packslip defines no evidence levels. Consumers record what they verified, as a SLSA verification summary or in their own terms, and set their own floor: which signing scheme, which signer, and whether provenance is required. Once a release clears that bar, the next one may not fall below it.

05 · Adoption

Publishing is one step. Consuming is six rules.

For vendors on GitHub

Add the action to the job that publishes your release, after the artifacts exist.

permissions:
  contents: write
  id-token: write
  attestations: write

steps:
  - uses: jdx/packslip@v1
    with:
      artifacts: dist/*.tar.xz dist/*.zip
      bin: mytool

That is the whole integration. The action attests build provenance for every artifact, writes the packslip, signs it with the job's identity, verifies the result, and uploads packslip.sigstore.json to the release. The project name defaults to the repository and the version to the tag.

Platforms are read from file names. Flags cover the rest: an executable whose PATH name differs from its file, two builds of one platform, the completions, man page, usage spec, skill, or desktop entry that ship alongside, and provenance you publish yourself. A monorepo runs the step once per tool with a subpath in the project name. The tooling section of the spec lists every option.

Everywhere else

The action wraps a plain binary, and the binary runs anywhere. In any CI system that issues OIDC tokens it signs keylessly. Elsewhere, generate a key once, keep the secret half in your secret store, and publish the public half so consumers can pin it. Either way the signature goes into the Rekor log.

cargo install packslip

packslip keygen -o release.key
packslip create \
  --project mytool.example.com \
  --version "$VERSION" \
  --key release.key \
  --out dist \
  --url-base "https://dl.example.com/mytool/$VERSION" \
  --bin mytool \
  dist/*.tar.xz

packslip releases --project mytool.example.com \
  --sequence 42 --valid-for 30d --key release.key \
  --release "https://dl.example.com/mytool/$VERSION/packslip.sigstore.json=dist/packslip.sigstore.json" \
  --out site/.well-known/packslip.json

For consumers

A package manager, a distribution repository, and a corporate mirror all follow the same rules.

  1. Pin the identity once. For a project on a forge, the name is the pin: accept only the forge's issuer and an identity under that repository. For a project on its own domain, pin its public key or identity. Never take a key from the document, and never trust a bundle's key hint.
  2. Verify the bundle, then the statement, then the digest and size of every artifact you downloaded.
  3. Never downgrade. Refuse a release signed with a weaker scheme than the last one you accepted, signed by someone new without a human approving it, or missing provenance the last release had. A keyless signer is its workflow path, so a new tag of the same workflow is the same signer.
  4. Wait before installing. Apply a minimum release age to the time the transparency log recorded, so a hijacked release is noticed before unattended installs pick it up.
  5. Order by semver. Every version is semver: precedence ranks releases, a prerelease part marks a prerelease, and its first identifier names the channel. Every project has a release list: GitHub's releases endpoint, or a signed list on the vendor's domain. It says what was released and what was withdrawn, nothing more. Refuse a stale signed list, never pick a yanked release, and skip prereleases unless asked.
  6. Never guess between two artifacts. Select by os, arch, libc, format, and variant. If two still match, stop.

The reference verifier takes the same pins as flags: --identity-prefix, or an exact --identity and --issuer, for keyless signers, and --pubkey for a key. It is also a Rust library, and packslip schema prints the JSON schema for everyone else.

06 · Who it is for

Built for the tools that install other people's binaries.

pacvamp

pacvamp is a trust-focused package manager for pacman-based distributions. It is meant to build vendor packages from the vendor's packslip instead of hand-edited checksum lines, re-verify against the project's identity, enforce a minimum release age and no-downgrade, and ship the packslip beside the package so a client can chain the repository's signature back to the vendor offline.

mise

mise has experimental support. Its github and http backends verify a packslip when a release ships one and record the result in mise.lock, so such a tool needs no registry entry. mise's own release workflow is meant to be the reference publisher. Until the spec is stable, treat all of this as something to test with, not to depend on.

Everyone else

Nothing in the format is specific to a distro or a vendor. A corporate mirror or a one-off install script can verify the same file against the same name.
